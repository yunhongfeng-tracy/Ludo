# LUDO · 一掷之间

版本：0.4.0，吃子与到家奖励再掷  
日期：2026年09月08日

一个玩家与电脑 1 对 1 对战的离线 Ludo 网页游戏。玩家使用红色，电脑使用黄色，双方各有 4 枚棋子。AI 是本地 JavaScript 策略，不接入 AI API，不需要后端、账号或数据库。

## 开始游戏

在线试玩：[LUDO · 一掷之间](https://ludo.tracyyun.cn/)。部署信息见[服务器部署说明](doc/服务器部署说明.md)。

1. 用桌面 Chrome 或 Edge 打开项目根目录的 `index.html`，也可以直接双击该文件。
2. 选择初级、中级、高级或终极，点击“开始对局”。先手由程序随机决定。
3. 轮到自己时点击掷骰，然后点击带箭头和深色外圈的合法棋子。电脑会自动完成其行动。
4. 先将全部 4 枚棋子送到终点的一方获胜。

`index.html` 是资源内嵌的单文件成品，运行时不需要网络，也不需要安装 Node。分享时可以只发送这个 HTML 文件。

当前对局不会自动保存。刷新或关闭页面会丢失本局进度；“重新开始”会先要求确认。页面提供玩法说明、双方到家进度、棋局动态和音效开关。

通过页头或页脚的“版本更新”查看发布历史，也可直接访问 [版本更新页面](https://ludo.tracyyun.cn/#updates)。记录内嵌在同一个 HTML 文件中，离线可读。查看记录时暂停新行动和 AI 搜索，返回游戏继续当前棋局；切换页面不会重新开局。

冒烟对局只验证系统能持续运行，不构成正式难度差异证据。当前也不宣称 AI 策略最优。最终目标是在浏览器可接受的思考时间内提高强度，并通过预先确定的测试证明相邻档位的区别。

高级和终极通过内嵌的 Web Worker 计算，界面保持可操作。它们枚举未来骰子的六种可能与对手应对，只采用已经完整搜索完的一层结果；节点或时间先达到上限时停止，不获取未来真实骰点。终极 v2 在双方所有未完成棋子进入专属归家通道后，还会尝试完整求解残局；只有全部候选都算完才采用其概率结果，未完成则使用剩余预算继续搜索。若浏览器不支持计算线程或线程失败，会显示“兼容模式”，用中级合法策略完成该步。重新开局会取消旧搜索。

当前桌面验收见[奖励再掷验收记录](doc/奖励再掷验收记录.md)，旧棋规的 0.3.0 对战见[终极 v2 验收记录](doc/终极v2验收记录.md)，0.2 历史结果保留在[阶段二验收记录](doc/阶段二验收记录.md)。各档的节点与时间参数是计算预算，不是胜率保证。

## AI 对战胜率

**以下为旧棋规 `basic-ludo-1v1@1` 的历史测试，尚未重新评测 v0.4.0 的吃子与到家奖励再掷规则。** 胜负与胜率均指对战组合左侧 AI，不同批次单独展示，不合并计算。

| 对战组合 | 胜 / 负 | 胜率 | 测试性质 |
| --- | ---: | ---: | --- |
| 中级 vs 初级 | 28 / 4 | **87.5%** | 32 局开发测试 |
| 高级 vs 中级 | 22 / 10 | **68.75%** | 32 局开发测试 |
| 终极 v2 vs 高级 | 34 / 30 | **53.13%** | 64 局独立验证，仅限制节点 |
| 终极 v2 vs 高级 | 8 / 8 | **50%** | 16 局启用实际时间预算的核对 |

前两组见[阶段二验收记录](doc/阶段二验收记录.md)，后两组见[终极 v2 验收记录](doc/终极v2验收记录.md)。这些样本尚未正式证明四档强度依次递增，终极 v2 对高级也未表现出明确优势。高级对初级、终极对初级、终极对中级尚无完整专项报告。

另外，0.2 的旧终极对高级为 16 胜 16 负，属于当时的 32 局开发批次，不能代表新版强度。

终极 v2 的[开发与测试计划](doc/终极v2开发与测试计划.md)、[策略机制说明](doc/终极v2策略说明.md)与[验收记录](doc/终极v2验收记录.md)分别记录计划、实际算法和测试证据。初级、中级、高级保留旧策略，旧终极源码冻结在 `tests/fixtures/ai-v1/`，用于独立对照。普通局面的估分不是获胜概率，局部精确求解也不自动证明整局强度。

0.3.0 候选的独立验证为：对冻结高级 34 胜 30 负，对冻结旧终极 38 胜 26 负，两组各 64 局，均无错误或截断。对高级的 53.125% 未达到预先约定的 55% 验证门槛，本轮不进入正式留出，也不宣称四档强度已证明有序。这些结果不与用于调参的开发对战合并。

另用不同种子进行产品限时核对，各 16 局，对高级 8 胜 8 负、对旧终极 6 胜 10 负。后者移除双方限时后按同种子重放，仍为 6 胜 10 负，16 局胜者全部相同。这些小样本单独记录，重放不算新增独立样本，不能只引用较好的节点验证结果宣称变强。

## 本版规则

- 双方共用 1 个六面骰子。摇动结束后才显示本次点数并开放走棋。
- 掷出 6 可以将一枚基地棋子放到起点，也可以移动场内棋子 6 格。
- 第一次、第二次连续掷出 6 后继续掷骰。连续第三次 6 不走棋并换人，前两次移动保留。
- 普通格恰好落到对手所在位置时，将该格全部敌方棋子送回基地。经过不吃子。
- 四个起点和四个星标格是安全格，双方可以同格，不发生吃子。
- 允许己方叠子，不形成路障，普通格叠子仍会被全部吃掉。
- 骰点必须刚好到达终点。超点的棋子本次不能移动。
- 没有合法走法时自动消耗本次骰点；前两次连续 6 即使无子可走，也继续掷骰。
- 吃子或单子到达 HOME 终点后奖励一次掷骰，进入归家通道不算到家。同一步与掷 6 等条件的奖励不叠加；奖励行动再次吃子或到家可再次获奖。最后一枚棋子到家立即结束。
- 非 6 骰点会清空连续 6 的计数，即使该步吃子或到家。奖励掷骰若无子可走按通常规则结算，不储存机会。

不同发行版的 Ludo 存在细则差异。上面列明本项目采用的唯一基础玩法，程序与 AI 使用同一套棋规。

## 修改与开发

开发工具需要 Node.js 与 npm。项目没有第三方 npm 依赖，游戏玩家无需这些开发工具。

在项目目录执行下列命令，脚本以 `package.json` 为准：

| 命令                | 用途                                 |
| ----------------- | ---------------------------------- |
| `npm run build`   | 将模板、样式和脚本内嵌，生成根目录 `index.html`     |
| `npm run check`   | 检查 JavaScript 语法、UTF-8、内嵌插槽和外部资源引用 |
| `npm test`        | 运行棋规与 AI 单元测试，等价于 `npm run test`   |
| `npm run smoke`   | 运行固定配置的自动对局冒烟测试                    |
| `npm run preview` | 启动仅监听本机的开发预览服务，访问终端输出的网址           |
| `npm run benchmark -- ...` | 运行可恢复的相邻档位评测，具体参数见 `doc/AI评测协议.md` |

修改源码后先执行 `npm run build`，再执行检查与测试。`preview` 提供 HTTP 开发预览，不替代直接打开本地 HTML 的离线验收。

主要文件：

| 文件                                                      | 内容                      |
| ------------------------------------------------------- | ----------------------- |
| `index.html`                                            | 可独立运行的网页成品，由构建脚本生成      |
| `src/index.template.html`、`src/styles.css`、`src/app.js` | 页面结构、样式和对局交互            |
| `src/engine.js`                                         | 浏览器与 Node 共用的纯函数棋规内核    |
| `src/ai-policy.js`、`src/ai.js`                           | 产品四档入口、保留的旧算法和共用概率搜索 |
| `src/ai-v2-eval.js`、`src/ai-v2-search.js`                 | 终极完成成本评分与搜索             |
| `src/ai-v2-endgame.js`、`src/ai-v2-combined.js`             | 限定残局求解与共享预算调度         |
| `src/ai-client.js`、`src/ai-worker.js`                    | 离线计算线程、请求身份、取消和故障恢复 |
| `src/releases.json`、`src/updates.js`                     | 版本记录数据与更新页导航            |
| `tests/`                                                | 规则、AI 测试与自动对局冒烟         |
| `tools/`                                                | 构建、检查和本地开发预览脚本          |
| `doc/AI策略系统设计.md`                                       | 完整策略设计的历史稿，不能作为功能已实现的证明 |
| `doc/分阶段开发计划.md`                                        | 分阶段范围、验收输出与当前进展         |

当前优先交付电脑浏览器版本，手机适配暂缓。原始需求与参考图片保留在项目中。后续安排见[分阶段开发计划](doc/分阶段开发计划.md)，本轮证据和覆盖边界见[终极 v2 验收记录](doc/终极v2验收记录.md)，基础体验的历史记录见[阶段一验收记录](doc/阶段一验收记录.md)。

## 维护版本记录

在 `src/releases.json` 的 `releases` 开头添加本次记录，填写版本、日期、标题、简述以及新增、优化或修复内容。只记录本次准备发布的实际改动，未实现的方案不列入发布历史。将 `currentVersion` 与 `package.json` 的 `version` 同步，再构建成品；构建会检查版本一致、日期倒序、记录 ID 唯一和编码，并转义记录文本。

更新页、页脚的版本号由构建自动填入。历史上的两次 0.1 体验补丁保留当时版本标记，并说明未单独编号。涉及页面切换时，可通过 `tests/browser-updates.cli.js` 验证离线入口、浏览历史、摇骰/移动/搜索中的暂停恢复和终局返回。
